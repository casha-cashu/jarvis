# JARVIS — agent guide

## Boundaries and local context

- Python entrypoint: `jarvis.cli:main`. Keep `Jarvis` in `jarvis/__init__.py` a thin orchestrator; configuration, audio, response routing, conversation state and lifecycle live directly under `jarvis/`, **not** `jarvis/modules/`.
- `jarvis/modules/` holds NLU, commands, LLM and audio engines; `jarvis/adapters/` holds platform implementations. NLU trains from `data/commands.json` + `data/apps.json`; legacy command matching is fallback.
- `jarvis-ui/` is the Tauri/React desktop app, not the website. Its Rust backend spawns `jarvis/ui_bridge.py` over stdin/stdout JSON; development uses root `venv/bin/python` (`JARVIS_PYTHON_ROOT` / `JARVIS_PYTHON` override this), packaged builds prefer the sidecar.
- `site/` is a separate Next.js app with a pnpm lockfile. Its `build` ignores TypeScript errors; it has no lint/test scripts. Checked-in `docs/` site assets are not regenerated by the current CI workflows.
- Use the existing root `venv/`. Personal `.env`, `config.yaml`, `opencode.jsonc` and session files `HANDOFF.md`, `SESSION.md`, `bridge.md` are gitignored; keep them so. Read `HANDOFF.md` for unfinished work, but verify its claims against the tree.
- Root instructions supersede `.opencode/AGENTS.md` and `.opencode/commands/*.md`: those reference deleted `jarvis-claude`, `jarvis-new`, `jarvis-github` trees. Skills live in `.opencode/skills/` + `.agents/skills/`; the audio skill also has stale cwd/venv paths.

## Commands and verification

Run from the repository root unless a directory is specified:

- Unit suite: `PYTHONPATH=. ./venv/bin/python -m pytest -m "not slow and not integration" -q`. `make test` uses the same filter with `python3` from `PATH`; activate the venv first.
- Focused test: `PYTHONPATH=. ./venv/bin/python -m pytest tests/test_env.py -v`; use `path/to/test.py::test_name` for one case.
- **Never run unfiltered `pytest tests/`**: integration tests open real audio/display devices and can hang. The `slow` marker also covers network/model downloads.
- Backend gate: `./venv/bin/ruff check jarvis/ tests/ && ./venv/bin/ruff format --check jarvis/ tests/ && ./venv/bin/python -m mypy jarvis/`. Mypy scope is `jarvis/`, not tests. The Python `dev` extra does not directly install Ruff/mypy; pre-commit manages its own copies.
- Rust gate: `cargo check --manifest-path jarvis-ui/src-tauri/Cargo.toml`.
- In `jarvis-ui/`: `npm ci`, then `npm run build && npm run lint && npm run test` (tsc+Vite, Oxlint, Vitest). CI uses Node 22. Focused test: `npm run test -- src/path/to/file.test.tsx`.
- GUI development: `npm run tauri dev` in `jarvis-ui/`; Tauri starts Vite on fixed `127.0.0.1:5173`. Its build hook builds the frontend, **not** the PyInstaller sidecar.
- Docker unit suites: `make docker-test-arch`, `make docker-test-debian`, `make docker-test-fedora`. Hardware integration: `make docker-integration-i3` / `make docker-integration-sway`; these targets supply required container permissions (Sway is privileged).
- After activating the venv: `jarvis run --dry-run` skips STT/TTS/VAD model loads; use `jarvis doctor` for environment/audio/config diagnostics.

## Contracts that are easy to break

- `jarvis/config_loader.py` expands `${VAR}` / `${VAR:-default}` and validates through `jarvis/config_schema.py`; missing variables without defaults warn and become empty strings. `JARVIS_CONFIG_PATH` is a fallback when the requested default config is absent, not an unconditional override.
- API keys flow through config/provider kwargs, never write them into `os.environ`. Every Python subprocess must pass `env=sanitized_env()` from `jarvis/_env.py`; no `shell=True`. Adapter command strings are split with `shlex.split`, so shell operators are literal arguments, not fallback chains.
- For time-sensitive/interactive commands (screenshot timestamps, `slurp` geometry), pass the method reference as `cmd`, not its result: `CommandExecutor._run` evaluates callables at execution time.
- `tests/conftest.py` isolates data/history/NLU cache/config through `JARVIS_*` variables and patches already-imported `llm.HISTORY_FILE` / `nlu.CACHE_DIR`. Use these fixtures rather than real user files; preserve the thin `Jarvis._load_config` hook patched by `jarvis_instance`.
- `check_sanitized_env` is an explicit fixture for subprocess-environment assertions, not an autouse check.
- Python minimum is 3.10; macOS CI uses 3.11. Vosk is an optional `.[vosk]` extra; prefer Whisper for fresh Python 3.13+ environments. `audioop-lts` is conditional on Python >=3.13. Importing `jarvis` still pulls heavy dependencies even for many unit tests.
- Docker installs dependencies before copying sources; install CPU Torch explicitly rather than pulling the default CUDA bundle. Preserve tested command exit codes, especially `pipefail` around macOS pytest output piping.

## Releases and packaging

- Synchronize versions in `pyproject.toml`, `jarvis-ui/package.json`, `jarvis-ui/src-tauri/{tauri.conf.json,Cargo.toml}` and `dist/arch/PKGBUILD`; update npm/Cargo lock metadata too. Do not assume existing lock metadata or README download examples are current.
- Also update displayed release versions in `docs/` HTML/TXT/JS (excluding `docs/site/`) and both `site/lib/github-release.ts` and `site/lib/use-release.ts` fallbacks. The site's own package version is independent.
- `.github/workflows/release.yml` publishes on `v*` tags, building the sidecar before Tauri packaging. Linux uses Ubuntu 22.04 for portable glibc; CI repacks the deb into Arch format and builds macOS ARM/Intel packages separately.
- `scripts/build_portable_docker.sh` is not a verification-only command: it changes mounted output ownership, copies packages outside the repo and optionally mirrors to removable media. Inspect it before running.
